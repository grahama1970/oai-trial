Abstract

Existing code benchmarks measure whether an agent can produce any test that reproduces a known bug, or whether it can produce a patch that fixes a described issue. Neither isolates the distinct skill of property-based testing: deriving a semantic invariant from documentation, and then constructing an input-generation strategy precise enough to make a random search reveal the violation. We introduce PBT-Bench , a benchmark of 100 curated property-based testing problems across 40 real Python libraries. Each problem injects one or more semantic bugs (365 in total, mean 3.65 per problem) designed so that default-strategy random inputs almost never trigger them; the agent must read the library’s documentation, identify the relevant invariant, and specify a Hypothesis @given strategy that concentrates mass in the trigger region. Bugs are stratified across three difficulty levels (L1–L3) spanning single-constraint boundary bugs to stateful, cross-function protocol violations. We evaluate eight contemporary LLMs under two prompting regimes (open-ended baseline vs. explicit Hypothesis scaffolding) for three independent runs per configuration. Bug recall under the PBT-guided prompt ranges from 42.1% to 83.4% across models; under the open-ended baseline, from 31.4% to 76.7%. Hypothesis scaffolding lifts mid-capability models by over 20 percentage points, but yields smaller gains for the strongest models, with two exceptions showing degradation, suggesting the structured prompt can interfere with certain model behaviours rather than complementing them. The hardest bugs prove model-specific: different architectures fail on different problems, leaving persistent gaps that no single model closes. We release the benchmark, harness, and full evaluation corpus to support downstream work on documentation-grounded semantic reasoning. Code is publicly available at https://github.com/ElliotXinqiWang/PBTbench and the dataset at https://huggingface.co/datasets/pbtbench-team/pbt-bench.

1 Introduction

Modern language models pass most code generation benchmarks when the expected behavior is stated concretely through input–output pairs. They do less well when the specification is abstract: a documented invariant that must hold across an entire input distribution rather than on any particular example. Property-based testing (PBT), introduced by QuickCheck (4) and popularized in Python by Hypothesis (16), is a testing methodology in which a programmer specifies (i) a property — a predicate that should hold universally — and (ii) a strategy — a typed, composable random-input generator — for sampling from the intended input distribution. The framework then searches for inputs that violate the property and shrinks any counterexample to a minimal failing form. A primer on Hypothesis strategies is in Appendix A.2. A minimal example of PBT is shown in Figure 1. We consider a buggy implementation of quicksort (qsort) that omits elements equal to the pivot at each recursive step. We verify two properties: the output is sorted, and it is a permutation (i.e., a multiset equivalent) of the input. We use the built-in lists strategy to sample random integer lists as inputs, which can generate cases with duplicate pivot values and thus trigger the assertion failure.

PBT provides greater coverage through random input exploration and expresses specifications as machine-checked, living documentation (24). However, writing a good property test is harder than a unit test (24; 8): the author must abstract from concrete outputs to invariants and design an input distribution that targets likely violations—a barrier that LLMs are naturally positioned to lower.

Recent benchmarks have begun to probe LLMs’ testing abilities, but none isolates the PBT skill. SWE-bench (11) rewards patch synthesis given a bug report; SWT-Bench (20) rewards test synthesis given a bug report; TestExplora (18) rewards test synthesis from documentation, but over a mined distribution of real-world pull requests that is dominated by bugs whose fixes include dedicated unit tests, I/O coupling, or integration-level failures. Terminal-Bench (17) evaluates agents end-to-end on terminal tasks with hand-crafted solutions but does not target any specific testing skill. Crucially, even when existing benchmarks withhold explicit bug reports, they only require agents to write finite, concrete test cases. None evaluates the conceptual leap unique to PBT: translating an abstract specification into universal invariants and programmatic input distributions.

We argue that evaluating PBT as a distinct skill requires curated — not mined — bugs, because not every bug is PBT-testable. A bug is PBT-testable only if (a) a semantic invariant of the API is violated, (b) the violation manifests under some expressible Hypothesis strategy without environmental mocks, and (c) the violation is deterministic under random input sampling. In practice, many real-world pull request bugs do not satisfy at least one of these conditions — common examples include UI rendering failures, database state dependencies, network ordering effects, and type errors that lack a corresponding documented invariant. A benchmark mined from PR history therefore conflates PBT skill with the agent’s ability to navigate around non-PBT-testable cases.

2 Related work

Benchmarks for patch synthesis.

SWE-bench (11) established the template for modern coding-agent evaluation: given a GitHub issue and the corresponding repository snapshot, an agent must produce a patch that passes a held-out reference test. SWE-bench Verified (21) curates a higher-signal subset, and more recent variants (SWE-bench Multimodal (33), SWE-Lancer (19), SWE-bench Pro/EVO (27)) extend scope and difficulty. Verified has effectively saturated (top scores exceed 85%85\% by early 2026), which has motivated both harder patch benchmarks and orthogonal skill benchmarks like ours. PBT-Bench does not ask the agent to fix the bug; it asks only whether the agent can expose it via a property test. Repair and exposure are known-distinct skills (20).

Benchmarks for test synthesis.

SWT-Bench (20) re-frames SWE-bench for test generation: given the issue description and buggy code, generate a test that fails on the buggy version and passes after the published fix. The fail-to-pass (F→\toP) criterion introduced there is the foundation of our own per-function evaluation; it traces to mined bug corpora such as Defects4J (12) and BugsInPy (30), though mining from version history does not guarantee PBT-testability. Two design differences distinguish PBT-Bench: (i) we withhold the bug description from the agent — the only oracle is the library’s own documentation — and (ii) we require the test to be a Hypothesis @given property, not an arbitrary concrete assertion. This precludes a class of trivial passes where the agent encodes the fixed behavior’s observable output as a literal.

Documentation-as-oracle test generation.

The closest benchmark in framing is TestExplora (18), which mines 2,389 doc-as-oracle test-generation tasks from GitHub pull requests. Its bug distribution is natural rather than PBT-filtered, so many tasks are concrete-assertion-testable or I/O-coupled; PBT-Bench complements it by isolating the PBT-specific skill on a controlled distribution.

General-purpose agent benchmarks.

Terminal-Bench 2.0 (17) evaluates agents on 89 hard terminal tasks; its construction protocol—three-reviewer verification, adversarial audits, and oracle-solution integrity—directly informs our QA pipeline (Section 3). HumanEval (1), LiveCodeBench (10), ClassEval (7), and AutoCodeBench (3) target code synthesis, not testing or bug exposure.

Property-based testing and LLMs.

LLM-based concrete test generators (ChatUniTest (2), CoverUp (23), CodaMosa (14), LIBRO (13)) produce input–output pairs; PBT-Bench requires instead a universal invariant paired with a typed Hypothesis strategy—a qualitatively different output. PBT originated with QuickCheck in Haskell (4), enabling automated random test execution against formal specifications. It has since been ported to many languages, including Python (Hypothesis (16)) and Scala (ScalaCheck (25)), and adopted in industrial settings for increasing testing confidence and finding edge-case bugs (24). Researchers have recently explored various approaches to integrate PBT with LLMs. 9 demonstrates that validating LLM outputs against PBT invariants improves pass@1 accuracy for code generation. 28 studies whether LLMs can generate property-based tests from API documentation, evaluating test quality against LLM-generated code mutants. While these works explore LLM-generated PBT, their evaluation relies on artificial mutants or simplified test targets, leaving it unclear whether agents can discover actual, stealthy semantic bugs in complex libraries. PBT-Bench bridges this gap by providing a rigorous F→\toP benchmark with 365 human-verified, deeply-injected bugs that closely mimic real-world invariant violations, evaluated on autonomous coding agents rather than static API calls. 31 improves PBT property generation via a multi-stage LLM workflow on Android applications (32). Unlike PBT-Bench, it uses static LLM API calls rather than coding agents and does not compare against direct LLM bug detection. LLM-augmented fuzzers such as TitanFuzz (5) and FuzzGPT (6) similarly exploit LLMs to generate inputs that expose bugs in deep-learning libraries, but operate at the level of raw programs without typed strategies or falsifiable predicates—the distinctions that make PBT a documented, reusable specification rather than a one-shot witness. A concurrent report (15) deploys an LLM agent in an open-ended PBT loop to find bugs in real Python packages; unlike that tool-oriented study, PBT-Bench uses injected, verified bugs with a fixed F→\toP harness, enabling controlled cross-model comparison.

3 The PBT-Bench Benchmark

PBT-Bench contains 100 curated property-based testing problems across 40 Python libraries. This section specifies the problem format (§3.1), the three-level difficulty taxonomy (§3.2), the curation and quality-assurance protocol (§3.3), and the fidelity argument for injected bugs (§3.4).

3.1 Problem format

Each problem contains a buggy library, agent-accessible documentation (docs/; the sole oracle), a passing existing test suite, and one or more reversible bug patches (bug_N.patch). Reversibility is key: the default container state applies all patches; removing patch NN yields the fixed-bug-NN configuration, enabling independent per-bug F→\toP scoring even when a problem contains multiple co-injected bugs. Full directory layout and metadata schema are in Appendix A.1.

PBT-testability criteria.

Every injected bug must satisfy four criteria, which are enforced during curation and re-verified by check_infra.py. Specifically, we require semantic, meaning the bug violates a documented invariant or contract rather than an implementation detail, including properties such as roundtrip identity, commutativity, monotonicity, bounded output ranges, and protocol preconditions; expressivity, meaning the invariant can be encoded as a @given property using Hypothesis’s built-in and @composite strategies without relying on external effects such as files, sockets, or clocks; stealth, meaning the bug is not easily detectable by short manual inspection and typically resides in under-tested code paths or is masked by locally plausible computations; and deterministic trigger, meaning there exists a well-defined input region TT on which the bug manifests with probability one (or a specific action sequence in the stateful case), with the ground-truth strategy concentrating probability mass on TT.

Two-container evaluation harness.

The benchmark is run in two independent containers per problem (Docker or Apptainer, depending on the host environment). The first (agent container) contains the buggy library, documentation, and existing test suite, and is handed to the agent under the OpenHands SDK (29) with the prompt template of the relevant mode. The second (eval container) is created after the agent writes pbt_test.py: for each injected bug bb, the harness restores the buggy library, runs each test function, then reverses only patch bb and re-runs. A bug is found when at least one test function passes the F→\toP predicate — fails on the buggy version and passes on the version with bb reversed — for that specific bug. This per-function, per-bug scoring correctly credits agents who write one test per bug in a single file.

3.2 Difficulty taxonomy

In Hypothesis, a strategy (SearchStrategy) draws random values from a typed search space and automatically shrinks any discovered counterexample to a minimal failing form. The @given(strat, …) decorator binds strategies to a test function’s arguments and drives the adaptive search engine; built-in primitives (st.lists(), st.integers(), st.floats(), etc.) and the @st.composite decorator cover most input structures. A fuller primer is in Appendix A.2. Each injected bug is labelled with one of three difficulty levels reflecting the minimum Hypothesis-strategy sophistication required for random search to hit the trigger region in under 200 examples. L1 corresponds to single-constraint bugs, where either Hypothesis’s default strategies suffice (e.g., boundary exploration triggers the bug with high probability) or the agent needs to identify a single input constraint such as a specific value range, size class, or structural property; the trigger probability under default strategies ranges from high to below one percent. L2 denotes multi-constraint triggers that require simultaneously satisfying several documentation-derived conditions, such as value ranges, structural constraints, and operation ordering. L3 captures cross-function or cross-operation protocol violations, which require tests over sequences of API calls or metamorphic tests (i.e., checking invariants across multiple executions), where the invariant spans multiple API calls.

Across the 100 canonical evaluation problems, the 365 injected bugs distribute as follows: L1 = 87 (24%24\%), L2 = 184 (50%50\%), L3 = 94 (26%26\%). The distribution is intentionally skewed toward L2–L3: early curation rounds consistently found that trivial single-constraint bugs were solved by both reference models in a single rollout, providing no discriminative signal; most were retired or relabelled.

3.3 Curation and quality assurance

Library selection.

Libraries were selected for rich internal-state invariants not directly observable through the public API, a substantial gap between the public interface and its implementation (making code-reading localization hard), documentation quality sufficient for doc-first trigger inference, and pure Python implementation. We excluded encode/decode core paths (roundtrip properties trivially cover their bugs) and libraries where patches are likely to conflict with internal self-use.

Bug design and retirement.

Problems were developed through an iterative design-evaluate-retire process in which an LLM-assisted design agent proposed candidate bugs and patches, and human authors reviewed each candidate for correctness, stealth, and PBT-testability before acceptance. After each design round, every candidate problem was evaluated against two reference models (Claude Sonnet 4.6 and GLM 5.1, each running the OpenHands baseline scaffold for a single rollout); problems on which both reference models achieved full recall were retired or redesigned, as unanimous success on a single rollout provides no discriminative signal. The difficulty bar was raised progressively across rounds as earlier problems proved easier than anticipated. Retired problems are archived in the repository as documented negative examples for future benchmark construction.

Each bug candidate was checked against a design checklist before acceptance: injection at least two call-chain layers below the public API surface; domain knowledge required to understand why the code is incorrect (the bug must not be obviously wrong from a local reading); the clean-pass criterion (the injected bug must leave the library’s existing unit test suite intact); for problems containing multiple bugs, each bug must be independently triggerable by a distinct input region that does not simultaneously trigger other bugs in the same problem (verified via pairwise testing of ground-truth strategies); and the existence of a ground-truth strategy derivable from documentation alone that finds the bug within the default example budget.

Three-stage QA pipeline.

Each accepted problem passed three verification stages. Stage 1 (automated) ran check_infra.py to verify clean patch application, upstream-test pass, trigger-path independence, and ground-truth solution validity. Stage 2 (reference-model gate) evaluated each problem under the two reference models defined above; problems where both achieved full recall were retired. Stage 3 (manual adversarial check) confirmed that each accepted bug satisfies the stealth criterion and that existing-test pass rates are unaffected. The Stage 3 protocol is the same one applied in Section 6.

3.4 Fidelity to real-world bugs

Controlled bug injection raises a representativeness concern. Our position: PBT-testability is a design constraint, not a distributional one — a benchmark evaluating PBT must select for bugs PBT could in principle detect. Within that constraint we preserve fidelity three ways. First, every injected bug falls into one of eleven classes empirically observed in open-source Python bug reports (off-by-one/boundary, wrong reference/expression, condition/logic inversion, wrong operator, argument/field order swap, missing operation, traversal/ordering, sign/direction error, protocol/domain-specific, wrong constant/value, and state corruption/mutation); the full taxonomy with counts is in Appendix A.5. Second, every bug satisfies the clean-pass criterion (defined in Section 3.3), matching the empirical fact that released semantic bugs escaped their own tests. Third, the 40 libraries span seven domains (serialization, data structures, date–time, type systems and schemas, numerics, state machines, parsing/HTML); the full library list is in Appendix A.4.

4 Experimental setup

We evaluate eight contemporary LLMs under two prompting regimes, each repeated three times per problem, over the 100-problem evaluation set. All configurations use the same OpenHands agent scaffold to isolate prompt and model effects from scaffold-specific tuning.

Models.

We evaluate Claude Sonnet 4.6, DeepSeek V3.2, Gemini 3 Flash, GLM 5.1, Grok 4.1 Fast, Qwen 3.6 Plus, Qwen 3.5-30B-A3B (Mixture-of-Experts, 3B active parameters), and Step 3.5 Flash. All models are queried through OpenRouter with the provider’s default temperature. Model release dates span April 2025 through February 2026.

Prompt regimes.

Each model is evaluated under two prompts:

  • •

    Baseline. An open-ended four-phase instruction — understand the library, find uncovered behavior, write a failing test, finalize — that does not mention property-based testing, Hypothesis, or @given. The agent is told only that a test must fail on the current library and pass after the bug is fixed. This measures general testing ability.

  • •

    PBT. An explicitly structured four-step instruction that names Hypothesis as the testing framework, requires @given decorators, and teaches the Roundtrip/Model-oracle/Invariant property taxonomy. The agent is instructed to write at least five focused test functions, each covering one documented invariant, without first hunting for a specific bug. This measures PBT ability under scaffolding.

The two prompt templates are reproduced verbatim in Appendix A.3. The comparison is an ablation of prompt-level scaffolding with all other variables held fixed. We verified post-hoc that no Baseline trajectory independently installed or imported Hypothesis, confirming the two conditions constitute a clean prompt ablation.

Agent scaffold.

All models run inside the OpenHands SDK v1.11.5 with the standard tool set (file editor, terminal, think) and a maximum of 200 tool-call iterations. Agent containers are built from python:3.12-slim with the target library preinstalled via a cached image layer per library. PBT-mode containers additionally preinstall Hypothesis; Baseline containers do not, though the agent may install it during its run. Each agent has 60 minutes of wall-clock time per problem.

Evaluation.

After the agent writes /workspace/pbt_test.py, the harness collects the set of test functions, then for each injected bug bib_{i}: (i) restores the buggy library from a pristine backup, (ii) runs each test function individually with a per-function timeout (120 s for Baseline, 300 s for PBT), (iii) reverses patch bib_{i}, (iv) re-runs each test function. A function is useful for bib_{i} if it fails on the buggy version and passes after bib_{i} is reversed. The bug is found if at least one function is useful for it. Our primary metrics are:

  1. (1)

    Bug recall — bugs​_​found/bugs​_​total\mathrm{bugs\_found}/\mathrm{bugs\_total}, averaged across problems; the headline metric.

  2. (2)

    Problem coverage — fraction of problems on which at least one bug is found; measures breadth.

  3. (3)

    Full recall rate — fraction of problems on which all bugs are found; measures depth.

  4. (4)

    Test precision — useful​_​test​_​functions/total​_​test​_​functions\mathrm{useful\_test\_functions}/\mathrm{total\_test\_functions}; a per-function quality signal independent of recall.

Reproducibility and decontamination.

All 4,800 trajectories, generated pbt_test.py files, and container build scripts are released under a permissive licence; one trajectory timed out and is recorded as not-found (Appendix A.14). Every problem file embeds the BIG-bench canary GUID (26) for training-corpus decontamination. Computational details and API costs are in Appendix A.15.

5 Results

We report results from 4,800 agent trajectories: eight models, two prompt regimes, three independent runs per cell, 100 problems per run. Unless otherwise stated, numbers in this section are averaged across the three runs.

5.1 Headline results

Table 1 reports the four primary metrics per (model, mode) cell. Three observations stand out.

(1) PBT scaffolding helps mid-capability models most.

The recall gap Δ=PBT−Baseline\Delta=\text{PBT}-\text{Baseline} ranges from +24.5+24.5pp (Qwen 3.6 Plus) down to −3.2-3.2pp (DeepSeek V3.2) and −8.0-8.0pp (Grok 4.1 Fast). Sonnet 4.6 sits at +6.7+6.7pp: PBT mode helps, but by less than the gap for Qwen 3.5-30B-A3B (+22.9+22.9pp). For the four models with the largest gaps (Qwen 3.6, Qwen 3.5-30B-A3B, Step, Sonnet), |Δ||\Delta| exceeds the sum of the two cells’ 95%95\% bootstrap CIs, so those signs are robust to resampling; for the remaining four models, the gaps are smaller than the CI widths and should be interpreted directionally. This suggests the prompt’s explicit property taxonomy and @given template is substituting for capability a weaker model lacks — not complementing a skill a stronger model already has. We analyze this further in Section 6.

(2) Problem coverage and full recall diverge; the benchmark is not saturated.

Sonnet 4.6 Baseline hits the highest problem coverage (98.0%) but a full recall rate of only 43.0%, frequently missing co-located bugs; PBT mode trades a small coverage drop (92.7%) for a large gain in full recall (67.0%), consistent with its instruction to write multiple focused tests rather than hunt for a single bug. No cell achieves full recall above 70%: Sonnet 4.6 PBT leaves 33.0% of problems partially unsolved, and for every model-mode pair at least one problem per run yielded no F→\toP test.

5.2 Ensemble upper bound

To separate capability limits from problem diversity, we define reliable coverage: a bug is reliably covered by a cell if found in at least two of three independent runs, smoothing over Hypothesis’s search stochasticity.

Figure 2 shows the greedy union curve. The best single cell is Claude Sonnet 4.6 PBT, which reliably covers 317 of 365 bugs (86.8%86.8\%); Qwen 3.6 Plus PBT follows at 303 (83.0%83.0\%). Greedily adding a second cell (Claude Sonnet 4.6 Baseline) lifts union coverage to 95.1%95.1\%; the full 16-cell ensemble reaches 99.5%99.5\%. Two bugs — BIDC-004 bug_3 (a stateful bidict invariant violation) and TMLK-005 bug_1 (a tomlkit container indexing bug) — are never reliably found by any cell; both are L3 bugs whose trigger requires a precise multi-step state sequence that no model reliably constructs within the 200-example budget (details in Appendix A.11). Two observations stand out. First, within-model mode complementarity provides the majority of the ensemble headroom: the same model in two modes (Sonnet PBT + Sonnet Baseline) accounts for 30 of the 46 marginal bugs (65%), lifting coverage from 86.8% to 95.1%. Cross-architecture additions contribute modestly (Step +9, Gemini +6, GLM +1), reaching the 99.5% ceiling. This suggests PBT and Baseline elicit complementary testing strategies even within a single architecture. Second, at the bug level, 2/3652/365 bugs remain out of reach of any cell within our max-iterations budget; at the problem level, the hardest-problem distribution (Appendix A.10) is richer.

6 Analysis

Baseline vs. PBT: scaffolding as capability supplement.

Section 5.1 noted that PBT scaffolding benefits mid-tier models far more than frontier ones, with the strongest model (Sonnet 4.6) seeing a +6.7+6.7pp bump and the weakest mainstream model (Qwen 3.5-30B-A3B, 3B active parameters) seeing +22.9+22.9pp. A plausible mechanism is that the PBT prompt provides three things the baseline does not: (i) an explicit framework choice (Hypothesis) that eliminates a planning step, (ii) a worked code template (@given(...) ... @settings(max_examples=200, deadline=None)), and (iii) a compact property taxonomy (Roundtrip, Model-oracle, Invariant, Boundary) that scaffolds the “what should I test” decision.

Consistent with this, PBT mode raises Qwen 3.5-30B-A3B’s test-file completion rate from 84% to 91% and average tool-call count from 29 to 48.

Diagnostics: difficulty, complementarity, failure modes.

Three short diagnostics support the headline numbers (full tables in Appendices A.9–A.12). (1) L1–L3 labels track empirical hardness: Sonnet-Baseline recall descends monotonically with L1/L2/L3 (79%/78%/68%79\%/78\%/68\%; n=87/184/94n=87/184/94); this ordering holds in 15 of 16 cells (Table 3), and averaged across all eight models the mean recall is 66%/60%/51%66\%/60\%/51\%. The L1/L2 gap is narrower than the L2/L3 gap as expected: both L1 and L2 require input-constraint reasoning (differing only in constraint count), while L3 additionally requires cross-function protocol understanding. (2) No model dominates the hardest bugs: the three GALS finite-field problems are each solved at different rates by different model families, so a cross-model union is required to cover them. (3) Baseline and PBT fail categorically differently. Over 20 sampled failures per (model, mode) cell classified into eight mutually-exclusive modes, Baseline failures are dominated by Incorrect Assertion (59%) and Overly Concrete Test (32%) — correct-looking tests aimed at the wrong invariant or missing the trigger region. PBT failures instead shift to search pathologies: Assume Misuse (31% overall, up to 75% for GLM 5.1), where the agent calls hypothesis.assume() on a predicate that excludes the bug’s trigger region, and Wrong Strategy Range (31%, up to 50% for Gemini 3 Flash). The Assume Misuse diagnostic is prompt-actionable: an explicit warning against assume()-based filtering should recover a substantial fraction of PBT-mode failures. (4) Scaffolding benefit is not uniform across difficulty levels (Table 3). For weaker models the Δ\Delta decreases with difficulty: Qwen 3.5-30B-A3B gains +35.2+35.2/+25.4+25.4/+14.8+14.8 pp on L1/L2/L3, suggesting the prompt substitutes for constraint-reasoning on easy bugs but cannot close the gap on L3 protocol violations. Step 3.5 Flash is the exception, showing a near-flat benefit (≈+22.5{\approx}+22.5 pp) across all three levels. Models for which PBT hurts overall show degradation concentrated on harder bugs: DeepSeek V3.2 shows +2.7+2.7/−4.0-4.0/−7.8-7.8 pp, and Grok 4.1 Fast −5.7-5.7/−5.2-5.2/−10.6-10.6 pp, a pattern consistent with the scaffold constraining rather than guiding their search on L2–L3 problems. Full per-cell breakdowns and analysis are in Appendix A.9.

Adversarial audit and data-integrity disclosure.

We ran two complementary integrity checks. (A) Under an explicit cheat prompt (adapted from Terminal-Bench’s exploited-audit protocol (17)), Claude Sonnet 4.6 was re-run on 30 trajectories; recall averaged 0.850.85–0.930.93, matching normal Baseline performance, and inspection found zero attack signatures (no hardcoded assertions, version-gated conditionals, or path manipulation), confirming F→\toP robustness to prompt-level gaming. (B) During early runs the harness left *.orig backup files readable by agents; all affected trajectories (8.0%8.0\%) were re-run on a fixed harness, and a paired test shows no significant recall effect (Wilcoxon p=0.31p=0.31); details are in Appendix A.7.

Run-to-run stability.

Three independent runs per cell suffice for reliable comparison: the median 95%95\% bootstrap CI half-width across all 16 cells is 3.83.8 pp (range 2.72.7–4.94.9 pp), and residual variance is attributable to Hypothesis’s internal search stochasticity rather than agent non-determinism. Full stability analysis and a post-hoc paraphrased-prompt sensitivity check are in Appendix A.13.

7 Conclusion

PBT-Bench probes a capability existing code-agent benchmarks implicitly assume: moving from a documented invariant to a Hypothesis strategy precise enough to expose a semantic bug. On 100 curated problems across 40 real Python libraries — all passing a PBT-testability screen and three-stage QA pipeline — property-based testing remains a persistent capability gap: the strongest current model reaches 83%83\% bug-level recall, and the 16-cell union still fails to reliably find two of 365365 bugs. Scaffolding toward Hypothesis disproportionately helps weaker-baseline models, indicating the prompt substitutes for a capability stronger models already carry in pretraining, rather than adding a skill. We release the benchmark, harness, and evaluation corpus; PBT-Bench complements test-synthesis benchmarks mined from PRs (TestExplora, SWT-Bench) by measuring depth on exactly the bug distribution for which PBT is the intended tool. Limitations. Curated bugs trade population fidelity for PBT-testability (§3.4); PBT-Bench covers only Python libraries with English-language documentation, and generalization to other languages is untested. All agents run on a single scaffold (OpenHands v1.11.5 with a fixed tool set); performance may differ under richer end-to-end systems such as Claude Code or Codex CLI that couple the LLM to a broader environment, and prompt sensitivity is only partially characterized (§A.13). The max_examples=200 budget likely caps L2/L3 recall on narrow-trigger problems (e.g. GALS-003, where the bug manifests only for specific random seeds within the budget window); a controlled budget sweep is left to future work. Future work. Raising max_examples to 1,000 would disentangle search-budget from strategy-quality gaps on L2/L3 bugs; adding an explicit assume()-misuse warning to the PBT prompt is a low-cost intervention expected to recover a substantial fraction of PBT-mode failures.

Appendix A Additional experimental details

A.1 Problem format

Each problem is stored in libraries/<lib>/problems/<ID>/ and consists of five components. problem.yaml defines metadata including library version, injected bugs with difficulty levels (L1–L3), trigger conditions, ground-truth Hypothesis strategies, and semantic tags (prop:*, bug:*, strat:*). Each injected bug is represented as a bug_N.patch unified diff applied at container startup, enabling reversible injection: the default state includes all patches; removing patch NN yields the fixed-bug-NN configuration for per-bug scoring. docs/ provides agent-accessible documentation (official sources when available), serving as the only external oracle. existing_tests/ contains unit tests that pass on the buggy version, ensuring injected bugs escape the baseline suite. ground_truth/ includes reference solutions and strategy specifications used exclusively for offline validation and never exposed to the agent.

A.2 Hypothesis strategy primer

In Hypothesis, a strategy (SearchStrategy) is an object that draws random values from a defined search space and automatically shrinks any discovered counterexample to a minimal failing form. The hypothesis.strategies module (aliased st by convention) provides built-in primitives — st.lists(), st.integers(), st.text(), st.floats() — and the @st.composite decorator for constructing structured, dependent strategies. The @given(strat, …) decorator binds one or more strategies to a test function’s arguments and drives the adaptive search engine. An example using st.lists() is shown in Figure 1.

A.3 Prompt templates

Below we present abridged versions of the two prompt templates used in the evaluation (full templates with Jinja2 conditionals are in eval/prompts/ in the released repository). Per-problem variables (library name, version, scope files) are filled at runtime.

Baseline prompt

⬇
You have been given a Python library to test. The library implementation
may have one or more issues that the existing test suite does not detect.
## Your task
Write a test that **fails** when run against the current (potentially buggy)
version of the library, and would **pass** after the issue is fixed.
Save your final test to ‘/workspace/pbt_test.py‘.
## Workspace layout
/workspace/
lib/ -- the library under test (may contain a bug)
docs/ -- API documentation and usage guide
existing_tests/ -- existing test suite (all currently pass; do NOT modify)
pytest.ini -- pre-configured: lib/ is already on the Python path
pbt_test.py -- write your test here
## Instructions
Phase 1 -- Understand the library
1.0 Inspect the scope files listed under Scope.
1.1 Read the documentation in /workspace/docs/.
1.2 Study the existing tests to understand what is already covered.
1.3 Identify the public API: what functions/methods exist, what are their contracts?
Phase 2 -- Find uncovered behavior
2.1 Think about what behaviors the existing tests do NOT cover.
2.2 Consider boundary conditions, edge cases, and properties that should always hold.
2.3 Look for semantic invariants: properties that should be true for all valid inputs.
Phase 3 -- Write a failing test
3.1 Write a test using pytest that exercises uncovered behavior.
3.2 The test should fail because of the bug in the current library.
3.3 Run: timeout 60 python -m pytest /workspace/pbt_test.py --tb=short -v
3.4 If the test passes, rethink your approach and return to Phase 2.
Phase 4 -- Finalize
4.1 Make sure the test file is saved at /workspace/pbt_test.py.
4.2 Confirm the test fails with a meaningful assertion error.
4.3 Do NOT modify any files in /workspace/lib/ or /workspace/existing_tests/.
Notes:
- Issues are subtle: the library mostly works, but fails silently on certain inputs.
- There may be more than one issue. Try to cover as many as possible.
- Write focused test functions: one specific potential issue per function.

PBT (Hypothesis-scaffolded) prompt

⬇
You have been given a Python library to test using Property-Based Testing (PBT)
with the Hypothesis framework. The library implementation may have one or more
issues that the existing test suite does not detect.
Your goal is NOT to find the bug first and then write a test for it. Instead,
write the most comprehensive set of property-based tests you can derive purely
from the documentation -- covering every behavior, invariant, and edge case
described. If the implementation deviates from its specification anywhere,
Hypothesis will find it.
## Strategy
Step 1 -- Read the documentation thoroughly
Read all files in /workspace/docs/. For each function or class in scope, extract:
- The precise semantics: what does it do, what does it return?
- All stated invariants: what should always be true?
- Edge cases mentioned explicitly
- Relationships between functions: roundtrip properties, monotonicity
- Any numeric thresholds, size limits, or type-specific behavior
Do NOT read the source code at this stage. The documentation is your oracle.
Step 2 -- Write as many property tests as possible
For every documented behavior or invariant, write a @given test. Aim for 5+
distinct test functions. Prefer:
- Roundtrip properties: decode(encode(x)) == x
- Model-based oracles: compare to a simple Python reference
- Invariant preservation: after any operations, a structural invariant holds
- Commutativity / associativity / idempotence
- Monotonicity: larger input -> larger (or smaller) output
- Boundary behavior: empty collections, single elements, min/max values
Use @settings(max_examples=200, deadline=None) on every test.
Step 3 -- Cover edge cases explicitly
Beyond general properties, write targeted tests for documented edge cases.
Step 4 -- Run and save
Run: python -m pytest /workspace/pbt_test.py --tb=short -v
Tests that fail immediately indicate you found a bug -- excellent.
Tests that pass are still valuable. Save all tests regardless.
## Rules
- Do NOT modify /workspace/lib/ or /workspace/existing_tests/.
- Every test must use @given from Hypothesis (not just fixed inputs).
- Write multiple focused functions -- one property per function.
- The documentation is your primary oracle.
- Do not spend time hunting for a specific bug. Write tests that cover
the spec broadly; Hypothesis will find the deviations.

A.7 The .orig leak: detection and rerun policy

The initial harness (patch -p1) occasionally left *.orig backup files readable by the agent. We fixed this in commit 1048fd6 by unconditionally deleting backups after patch application.

Detection.

We flag a workspace as “exploited” if its chat.md contains any regex match against five read-action patterns targeting .orig files (shell diff, cat/head/tail, grep, Python open, or file_editor view). In total, 383383 of 4,8004{,}800 workspaces (8.0%8.0\%) matched.

Rerun policy.

If any of the three runs for a (model, mode, problem) tuple contained exploitation, we reran all three runs on the post-fix harness. This affected 224224 tuples (672672 workspaces) across six models. The merged dataset used for all reported numbers contains zero residual pre-fix rows for any contaminated tuple.

Statistical effect.

Within-problem paired tests (Wilcoxon signed-rank p=0.31p=0.31, n=160n=160 mixed tuples) show no detectable causal effect of exploitation on recall. The rerun is a hygiene measure, not a correction for inflated scores.

A.8 Failure-mode taxonomy: method and examples

Classifier.

Failures were classified by a deterministic rule cascade implemented in paper/analysis/build_failure_taxonomy.py. The classifier consumes three signals per failed trial: (i) the submitted pbt_test.py source, examined for @given, assume(…) calls, default-strategy constructors like st.integers() or st.text(), and weak-assertion patterns (is not None, len(x) >= 0, isinstance, round-trip encode/decode); (ii) the per-function pass pattern on (buggy, fixed) library versions from bugs_result.json; (iii) chat.md for the complete agent interaction history. The cascade and its outputs across 320 sampled failures are in paper/analysis/failure_taxonomy.csv.

Sampling.

For each of the 16 (model, mode) cells we sampled 20 failures uniformly over problems, subject to test_file_found=True AND found=False. Across cells: 320 samples.

Representative examples.
  • •

    Assume Misuse — Sonnet 4.6 PBT on H5LB-003 bug 2: assume(val1 != val2) filters out the exact duplicate-value case that is the bug’s trigger.

  • •

    Assume Misuse — Sonnet 4.6 PBT on SRTD-005 bug 2: assume(query not in sl) — the bug is specifically about duplicate-query lookups.

  • •

    Wrong Strategy Range — DeepSeek V3.2 PBT on DCAC-005: @given(st.integers()) for a cache-expire timestamp, making triggers at boundary seconds astronomically unlikely.

  • •

    Wrong Strategy Range — DeepSeek V3.2 PBT on CTRS-001: st.text(alphabet=st.characters(whitelist_categories=(’L’,’N’,’P’,’S’,’Z’))) excludes control characters that the bug targets.

  • •

    Flaky Oracle — Grok 4.1 Fast Baseline on ICAL-003: oracle reads the serialized string back via Calendar.from_ical(ical_str.encode()) — the same buggy parser that produced the value.

  • •

    Incorrect Assertion — DeepSeek V3.2 Baseline on H5LB-003: a test asserts that &#x41; parses to ’A’, but the test’s expected value is itself what the buggy consumeNumberEntity produces — fails on both buggy and fixed libraries.

  • •

    Setup Error — DeepSeek V3.2 PBT on SYMP-005: duplicate from hypothesis import strategies as st and import hypothesis.strategies as st produce a collection-time crash; test functions never run.

  • •

    Under-Specified Property — DeepSeek V3.2 Baseline on PYCR-002: assert return_match is not None checks only the existence of some return statement, silent on whether it has the right shape.

Model-specific observations.
  • •

    Sonnet 4.6 and GLM 5.1 over-use assume(): they understand Hypothesis well enough to write generators, but also willingly filter out the trigger region.

  • •

    Qwen 3.5-30B-A3B and Gemini 3 Flash mostly fail on unbounded default strategies (45–50% Wrong Strategy Range).

  • •

    Step 3.5 Flash Baseline skews Overly Concrete (80%) — it writes a handful of hardcoded examples when it could write a property test.

Taxonomy adequacy.

After two rule-cascade refinements (splitting baseline “overly concrete” failures by their (buggy, fixed) pass pattern; excluding from hypothesis import assume false-positives from the Assume-Misuse regex), zero failures landed in the OTHER bucket. We take this as evidence that the eight categories are collectively sufficient for PBT failure analysis at the granularity of a deterministic classifier.

A.9 L1–L3 difficulty validation (empirical)

Figure 4 plots the confusion matrix of author-assigned L1–L3 against empirical difficulty buckets (Easy: Sonnet-Baseline passrate ≥2/3\geq 2/3; Medium: ≥1/3\geq 1/3; Hard: <1/3<1/3). Mean Sonnet-Baseline passrate is 79%79\% for L1 bugs (n=87n=87), 78%78\% for L2 (n=184n=184), and 68%68\% for L3 (n=94n=94). Medians are 1.01.0 for all three levels (Sonnet Baseline finds these on all three runs when it finds them at all), so the difficulty signal is carried by the mean, not the median; the distinction emerges in the left tail of each distribution.

The L1/L2 passrate gap is tighter (79%79\% vs. 78%78\%) than the L2/L3 gap (78%78\% vs. 68%68\%). This is expected: L1 and L2 both involve input-constraint reasoning (differing in the number of simultaneous constraints), while L3 additionally requires cross-function protocol understanding — a qualitatively different skill. The gap widens when averaging across all models (L1: 66%66\%, L2: 60%60\%, L3: 51%51\%), confirming that the three levels separate empirically distinct difficulty strata. Labels are assigned prospectively at design time, before any model evaluation, to avoid circularity.

Table 3 reports per-cell recall broken down by difficulty level. In 15 of 16 cells, recall decreases monotonically with difficulty (L1 >> L2 >> L3); the sole exception is GLM 5.1 Baseline, where L2 exceeds L1 by 2.2 pp — within the bootstrap CI width.

Per-difficulty Δ\Delta patterns.

The following observations are exploratory: per-difficulty Δ\Delta values are not accompanied by per-cell confidence intervals, so small differences should be interpreted cautiously.

(a) Diminishing-return pattern. Qwen 3.5-30B-A3B shows the clearest gradient: +35.2+35.2/+25.4+25.4/+14.8+14.8 pp on L1/L2/L3. One interpretation is that the scaffold supplies a framework choice and input-constraint template sufficient for L1 bugs (single-constraint boundary checks) but insufficient for L3 bugs requiring cross-function protocol reasoning. This pattern is specific to Qwen 3.5-30B-A3B; Qwen 3.6 Plus (+25.3+25.3/+25.5+25.5/+22.7+22.7 pp) is near-flat and grouped with the uniform-benefit pattern below.

(b) Uniform-benefit pattern. Step 3.5 Flash and Qwen 3.6 Plus achieve near-constant Δ\Delta across all three difficulty levels (≈+22.5{\approx}+22.5 and ≈+24.8{\approx}+24.8 pp respectively). This is consistent with the scaffold supplying a coverage discipline (“write five focused tests, one invariant per function”) that benefits these models roughly equally regardless of bug difficulty.

(c) Difficulty-amplified degradation. DeepSeek V3.2 and Grok 4.1 Fast show negative overall Δ\Delta, with greater degradation at higher difficulty (DeepSeek: +2.7+2.7/−4.0-4.0/−7.8-7.8 pp; Grok: −5.7-5.7/−5.2-5.2/−10.6-10.6 pp). One possible explanation is strategy over-specification: the PBT template may constrain the input search in ways that are tolerable for L1 bugs but exclude the narrower trigger regions of L2–L3 bugs, consistent with the elevated search-related failure rates documented for these models in Appendix A.12. Gemini 3 Flash shows a weaker version at L3 only (−0.4-0.4 pp, likely within noise) while retaining positive Δ\Delta at L1/L2 (+8.8+8.8/+12.9+12.9 pp), making it a borderline case between patterns (b) and (c).

(d) Large-Δ\Delta-at-L1 pattern. Sonnet 4.6 shows its largest absolute Δ\Delta on L1 (+13.8+13.8 pp), smaller at L2/L3 (+5.7+5.7/+6.4+6.4 pp). Sonnet 4.6 Baseline already achieves 79.3%79.3\% on L1 — leaving limited headroom — so the large L1 gain is notable; diminishing gains at L2/L3 may partly reflect that ceiling. GLM 5.1 shows the same ordering (+7.3+7.3/+3.7+3.7/+6.3+6.3 pp) but its Baseline L1 of 68.6%68.6\% is not near ceiling, so the explanation is less clear-cut.

We speculate that these patterns are consistent with two roles for PBT scaffolding: a framework bootstrapping role (consistent with patterns b and d) that supplies the Hypothesis API and coverage discipline; and a constraint elicitation role (consistent with pattern a) that substitutes for input-reasoning skills with diminishing returns as bug complexity grows. Whether these roles are genuinely separable, and why some models are harmed by scaffolding, would require controlled ablations — for instance, prompts that supply only the framework name versus prompts that add the full property taxonomy.

A.10 Cross-model bug-finding complementarity

Not every hard bug is hard for every model. The three galois library problems (GALS-003–005) illustrate this: each requires deep algebraic domain knowledge (finite-field arithmetic, LFSR protocols, polynomial factorization), yet model rankings are inconsistent across them.

  • •

    GALS-003 — Sonnet Baseline achieves 100% recall while several weaker models score ≤33%\leq 33\%; yet DeepSeek PBT and Qwen 3.6 PBT also reach 100%.

  • •

    GALS-004 — Qwen 3.6 PBT leads at 83%, while Sonnet PBT scores 67% and DeepSeek PBT only 17%. No model achieves full recall.

  • •

    GALS-005 — Gemini Baseline (92%) and Qwen 3.6 PBT (92%) lead; Sonnet Baseline scores 83% but Sonnet PBT drops to 58%.

This is not a general-capability inversion: Sonnet dominates overall recall. Rather, it indicates that PBT-Bench exposes problems for which specific model architectures or scaffolded reasoning paths may be differentially advantaged. For benchmark users, the actionable consequence is that combining test files across models is a recall-enhancing strategy.

A.11 Never-found bugs

Two of 365 bugs are never reliably found (found on ≥\geq2 of 3 runs) by any of the 16 (model, mode) cells:

  • •

    BIDC-004 bug_3 — a stateful bidict invariant violation requiring a specific sequence of put/forceput operations that triggers an internal node-count desync. The trigger probability under default strategies is near zero.

  • •

    TMLK-005 bug_1 — a tomlkit container indexing bug where unwrap() silently drops a nested inline table when a specific combination of dotted keys and inline-table nesting is present. Requires a composite strategy generating nested TOML structures of depth ≥\geq3.

Both are L3 bugs requiring cross-operation protocol knowledge. Their resistance to all evaluated models confirms the benchmark ceiling is meaningful.

A.12 Failure-mode taxonomy (full)

To characterize how agents fail, we sampled 20 failed trajectories per (model, mode) cell (320 samples, uniform over problems) and classified each into one of eight mutually-exclusive failure modes. Classification is rule-based over the submitted pbt_test.py combined with per-function buggy/fixed pass patterns; a PBT-specific refinement of the MAST taxonomy of 22 and the trajectory-level analysis of 17. Full categorization rules and per-sample outputs are in Appendix A.8 and the released paper/analysis/failure_taxonomy.csv.

Baseline vs PBT mode shows categorically different failure profiles.

In Baseline mode (n=160n=160 classified failures), 59% of failures are Incorrect Assertion (the test’s expected values are wrong — assertions fail against both buggy and fixed libraries because the agent fabricated incorrect outputs), 32% Overly Concrete Test (a few hardcoded inputs that happen not to intersect the bug’s trigger region), 8% Flaky Oracle (agent re-uses the library under test as its own oracle, typically via a round-trip encode/decode whose asymmetric failure is masked), and 1% Under-Specified Property. This pattern says Baseline agents correctly construct tests but aim them at the wrong invariant.

In PBT mode (n=160n=160), failure shifts to search pathologies. The single largest PBT-failure category is Assume Misuse (31% across PBT cells, peaking at 75% for GLM 5.1, 50% for DeepSeek V3.2, and 40% for Sonnet 4.6): the agent successfully designs a @given test but calls assume() on a predicate that happens to exclude the bug’s trigger region — e.g. assume(val1 != val2) in a test for a duplicate-value bug. The Hypothesis engine then never samples the triggering input. A second major PBT failure is Wrong Strategy Range (31% across PBT cells, peaking at 45% for Qwen 3.5-30B-A3B and 50% for Gemini 3 Flash): st.integers() where st.integers(min_value=32768, max_value=65535) is needed, for example. In PBT mode, Baseline’s dominant Incorrect Assertion drops to 21% (from 59%) and Overly Concrete Test vanishes (0%0\%), because the prompt’s @given template makes concrete-only tests syntactically unusual.

This is a previously-unreported diagnostic specific to property-based-testing evaluation: even when an agent correctly chooses Hypothesis, its most common failure mode is filtering out the counterexample region with assume(). Table 4 reports per-cell percentages; concrete examples are in Appendix A.8.

Implication for prompt design.

The Assume Misuse finding is actionable: a PBT-scaffolding prompt that warns explicitly “do not use assume() to skip inputs that look suspicious; inputs that look suspicious are exactly the ones that expose the bug” is likely to recover a substantial fraction of PBT-mode failures across most tested models. We leave empirical verification to future work.

A.13 Run-to-run stability (full)

All headline metrics are computed over 33 independent runs per (model, mode) cell and reported with 95%95\% percentile bootstrap confidence intervals (1,0001{,}000 resamples over problems ×\times runs). Across the 16 cells in Table 1, the Recall CI half-width ranges from 2.72.7 pp (Sonnet Baseline) to 4.94.9 pp (Step PBT), with a median of 3.83.8 pp. These intervals are narrow enough that every sign claim in Section 5 — including all PBT-vs-Baseline Δ\Delta values — survives resampling.

Residual variance is traceable to Hypothesis’s internal search procedure, not agent non-determinism. The GALS-003 case discussed in Appendix A.10 is the canonical example: the agent’s strategy correctly targets polynomials in GF⁡(q)\mathrm{GF}(q), but only some random seeds generate one with the specific ≥3\geq 3-distinct-degree-factor structure required to trigger the bug within the default max_examples=200 budget. For problems with known narrow triggers, raising max_examples to 1,0001{,}000 or higher would tighten the intervals further; a controlled study of this budget parameter is left to future work.

Post-hoc prompt check.

After the main runs, we wrote two paraphrased variants of each prompt (baseline_v{2,3}.j2 and pbt_hypothesis_v{2,3}.j2) and ran Sonnet 4.6 on all 100 problems under each variant (single run per variant) to check that headline recall is not an artifact of a particular phrasing.

Baseline mode. Original (3-run mean): 0.7650.765; v2: 0.7870.787; v3: 0.6500.650. The original and v2 are within seed noise of each other (the three seeds of the original prompt span 4.34.3 pp), while v3 is clearly worse.

PBT mode. Original (3-run mean): 0.8340.834; v2: 0.7620.762; v3: 0.8420.842. The original and v3 are within seed noise (the three seeds of the original span 7.67.6 pp), while v2 is clearly worse.

In both modes we kept the original prompt for the reported numbers. We flag that Baseline v2 and PBT v3 are equally defensible choices and release all candidates in eval/prompts/; a full sensitivity study (more models, more seeds per variant) is left to future work. To our knowledge, no comparable benchmark paper (SWE-bench, SWT-Bench, Terminal-Bench, LiveCodeBench) reports a multi-model prompt-paraphrase sweep; our single-model check already exceeds field norms. The large v3 Baseline drop (−11.5-11.5 pp) is most plausibly attributable to an inferior paraphrase rather than fundamental instability, given that the concurrent v2 variant deviates by only +2.2+2.2 pp.

A.14 Eval-phase timeout

One tuple (glm51 ×\times PBT ×\times run 3 ×\times GALS-005) hit the harness’s eval-phase wall-clock limit. The agent produced 96 @given test functions; during the per-function F→\toP scoring loop, repeated pytest 300-second timeouts accumulated past the 1,800-second eval-phase budget. That trajectory’s four bugs are recorded as detection_method=eval_phase_timeout / found=False rather than re-tried indefinitely. This is the sole abort in the 4,800-trajectory corpus. The harness now exposes an --eval-timeout flag (default 1,800 s) to make this failure mode explicit for future runs.
